# Internal Design

## 全体構成

無料版では、CLI起動後に以下の順番で処理する。

1. クリップボードからログ文字列を取得する
2. ログ文字列を行単位に分割する
3. エラーらしい行を抽出する
4. 抽出したエラー行から簡易分析結果を作る
5. 分析結果をコンソール表示用に整形する
6. コンソールに表示する

## 責務分離

- CLI制御: 処理全体の流れを管理する
- 入力処理: クリップボードからログ文字列を取得する
- 抽出処理: エラーらしい行を抽出する
- 分析処理: エラー行から見て取れる範囲で簡易説明、原因候補、確認ポイントを作る
- 表示処理: 結果をコンソールに表示しやすい形に整え、言語種別やヒントを読みやすく表示する

## 入力処理

- クリップボードから文字列を取得する
- 取得した文字列が空の場合は、空として扱う
- 入力処理ではエラー判定を行わない

## 抽出処理

- ログ文字列を1行ずつ確認する
- 判定キーワードを含む行をエラー候補として抽出する
- 大文字・小文字の違いは区別しない
- 抽出結果には、元ログ上の行番号とエラー行の文字列を含める
- 抽出処理では簡易説明や原因候補を作らない

## 分析処理

- 抽出済みのエラー行を対象にする
- ログ全体から言語の特徴を確認し、`language_hint` を作る
- `language_hint` は単一キーワードの即決ではなく、言語ごとの特徴を点数化して判定する
- 言語判定用の特徴は、強いヒントと弱いヒントに分ける
- 強いヒントは、特定言語のログ形式に近い文言として大きく加点する
- 弱いヒントは、複数言語で出る可能性がある文言として小さく加点する
- 一定点数に満たない場合や同点で判断できない場合は、`不明` とする
- `language_hint` がある場合は、該当言語の分析ルールを優先して判定する
- エラー行に含まれる例外名やキーワードから簡易分析する
- エラー種別ごとの簡易説明を作る
- エラー行から見て取れる範囲の原因候補を作る
- よくある確認ポイントを作る
- Python / Java / C# / JavaScript / SQL の代表的なエラーを対象にする
- 分析ルールは、頻度が高く具体的なキーワードを優先し、`error`、`warning`、`exception` のような広いキーワードは後ろに置く
- エラー本文から型名、属性名、変数名などのヒントを取り出せる場合は、必要な分析ルールにだけヒント抽出ルールを持たせる
- ヒント抽出では、同じエラー行を全ルールで再判定しない
- ヒントは確認ポイントに結合せず、分析結果の独立した値として扱う
- 判断できない場合は「不明」とする
- ログ全体の文脈、ソースコード、実行環境、外部AI APIを使った複雑な推測は行わない

## 表示処理

- 分析結果を外部設計で決めた形式に整形する
- 元ログ上の行番号を表示する
- エラー行を表示する
- 判定に使った言語種別を表示する
- 簡易説明、原因候補、確認ポイントを表示する
- ヒントがある場合は、確認ポイントとは別のヒント行として表示する
- 日本語ラベルの表示幅を考慮し、読み始め位置を揃える
- エラー行がない場合は、見つからなかったことを表示する
- 表示処理では抽出判定や分析判定を行わない

## データの流れ

1. クリップボードからログ文字列を取得する

```text
clipboard_text: str
```

2. ログ文字列を行単位で扱う

```text
lines: list[str]
```

3. エラー候補行を抽出する

```text
error_lines: list[ErrorLine]
```

各要素は、`ErrorLine` として元ログ上の行番号とエラー行を持つ。

```text
ErrorLine(
  line_number=12,
  text="ValueError: invalid literal for int() with base 10: 'abc'"
)
```

4. ログ全体から言語ヒントを作る

```text
language_hint: str
```

言語ヒントは、ログ全体を小文字化した文字列に対して、言語ごとの特徴キーワードを点数化して作る。
言語を判断できない場合は、共通ルールを優先できる値として扱う。

```text
language_scores: dict[str, int]
```

スコア計算では、以下を基本方針とする。

- `log.lower()` は最初に1回だけ作る
- 判定キーワードは小文字で管理する
- 強いヒントは `+3`、弱いヒントは `+1`、複数文言の組み合わせヒントは `+4` とする
- 最低判定点は `3` とし、最高点が `3` 未満の場合は `不明` とする
- 最高点が同点の場合は、無理に断定せず `不明` とする
- 必要な場合だけ、複数文言の組み合わせボーナスを加える
- 正規表現は言語判定では多用せず、まずは文字列検索を優先する
- 正規表現が必要な場合は、コンパイル済み正規表現を使う

5. エラー候補行を簡易分析する

```text
analysis_results: list[ErrorAnalysis]
```

各要素は、`ErrorAnalysis` としてエラー行、簡易説明、原因候補、確認ポイントを持つ。

```text
ErrorAnalysis(
  error_line=ErrorLine(
    line_number=12,
    text="ValueError: invalid literal for int() with base 10: 'abc'"
  ),
  language_hint="Python",
  description="値の変換に失敗した可能性があります。",
  cause_candidate="数値に変換できない文字列をint()などに渡している可能性があります。",
  check_point="入力値、型変換前の文字列、空文字や想定外の値が入っていないかを確認してください。",
  hint=None
)
```

6. 表示用文字列に整形する

```text
output_text: str
```

## 関数設計

### main

CLI起動時の入口。
入力、抽出、表示の流れを呼び出す。

- 入力: なし
- 出力: なし

### get_clipboard_text

クリップボードから文字列を取得する。

- 入力: なし
- 出力: クリップボード内の文字列

### extract_error_lines

ログ文字列からエラーらしい行を抽出する。

- 入力: ログ文字列
- 出力: `list[ErrorLine]`

### ErrorLine

1件のエラー候補行を表すデータ型。

- `line_number`: 元ログ上の行番号
- `text`: 元ログのエラー行文字列

### detect_language_hint

ログ全体から言語の特徴を探し、分析ルールの優先順を決めるためのヒントを作る。

- 入力: ログ文字列
- 出力: 言語ヒント文字列

判定方針:

- Python / Java / C# / JavaScript / SQL ごとにスコアを持つ
- 強いヒントが見つかった場合は `+3` する
- 弱いヒントが見つかった場合は `+1` する
- 特定の文言の組み合わせが見つかった場合は `+4` する
- 最も点数が高い言語を返す
- 最高点が `3` 未満の場合、または同点で判断できない場合は `不明` を返す
- `Java` と `JavaScript` は部分一致ではなく、スコア辞書のキーとして別々に扱う

### AnalysisRule

エラー種別ごとの判定条件と表示内容を表すデータ型。

- `keyword`: エラー行に含まれていたら、このルールを使う判定文字列
- `language_hint`: どの言語向けのルールかを表す文字列
- `description`: エラー種別の簡易説明
- `cause_candidate`: 原因候補
- `check_point`: よくある確認ポイント
- `hint_rule`: 必要な場合だけ持つ、エラー本文から追加ヒントを取り出すためのルール

### HintRule

エラー本文から型名、属性名、変数名などを取り出すためのルール。

- `pattern`: エラー本文から情報を抜き出すための正規表現
- `template`: 抜き出した情報を確認ポイントへ追加するための文面

### analyze_error_lines

抽出済みのエラー行から簡易分析結果を作る。

- 入力: `list[ErrorLine]`、言語ヒント
- 出力: `list[ErrorAnalysis]`

### ErrorAnalysis

1件のエラー候補行に対する簡易分析結果を表すデータ型。

- `error_line`: 元のエラー候補行
- `language_hint`: 判定に使った言語ヒント
- `description`: エラー種別の簡易説明
- `cause_candidate`: 原因候補
- `check_point`: よくある確認ポイント
- `hint`: エラー本文から取り出した追加ヒント。ヒントがない場合は `None`

### format_result

分析結果を表示用文字列に整形する。

- 入力: 簡易分析結果一覧
- 出力: 表示用文字列

## 有料版との境界

Public repository では、エラー行から見て取れる範囲の簡易分析までを扱う。
ログ全体の文脈、ソースコード、実行環境、外部AI APIを使った複雑な原因推測は扱わない。
有料版で必要になる詳細分析処理は Private repository 側で設計・実装する。

## 将来拡張の余地

- 無料版の簡易分析ルールを増やす
- Private repository 側で外部AI API連携を検討する
- ファイル入力に対応する
- 言語ごとの切り替え機能を追加する
- エラー件数の集計に対応する
- エラー傾向分析に対応する
- 出力形式を切り替えられるようにする
- 判定キーワードを設定ファイルで変更できるようにする
